契约卡（docs/contracts/）

用途：让并行的子代理能"接得上"，而不靠互相读聊天记录。
一张卡 = 一个系统开工需要知道的全部。开工前读自己的卡 + 直接上游的卡，就够动手。

一、八张卡

系统卡一句话
roadroad.md空间真值的源头：三表 + 围合面 + 可达性（事件驱动）
utilityutility.md市政容量与覆盖，必须排在 zoning 之前
zoningzoning.mdblock_face → parcel → 建筑（日更 + 月汇总）
populationpopulation.md人与迁徙，个人全量存、出行交给 traffic
employmentemployment.md岗位与产能，把人与路连起来
servicesservices.md半径型公共服务（一个标量 + 衰减）
financefinance.md核心循环引擎：地价 → 卖地 → 建校 → 地价
traffictraffic.md流与堵；宏观流量是真值，agent 只是表现

二、三条使用规则

1. 卡不是真相，是压缩

真相在：../design/system-boundaries.md §三（归属与 bus key）、../design/09-core-tick.md §7.4（已实现接口）、 ../../config/sim/&lt;系统&gt;.json（参数）。 卡与文档冲突时以文档为准，并回头修卡——卡过期比没有卡更坏。

2. 改卡 = 改契约 ⇒ 先提裁定

任何一条（新增 bus key、改字段、改频率、改降级默认值）都会影响下游。 流程：提 ../decisions.md → 拍板 → 改卡 → 改文档 → 通知所有下游的卡 → 再动代码。

⚠ 禁止"先加个字段，以后再补文档"——这正是 v1 的做法。

3. 并行时只读卡，不读别人的代码

子代理 A 不需要知道 B 怎么实现，只需要知道 B 会写哪些 key、什么时候写、缺数据时给什么。 这就是"上下文互通"的正确形态：共享契约，不共享对话。

三、开工前的四件套（每个子代理都要做）

1. 本系统的卡               ← docs/contracts/<自己>.md
2. 直接上游的卡（1–2 张）    ← 知道"我读的东西什么时候写、缺了给什么"
3. 09 §7.4 已实现接口        ← 别重造 Clock / Bus / Sim / SaveGame / Check
4. config/sim/<自己>.json    ← 参数从这里读，不写魔法数字（L5）

上游关系（读谁）：

road ─→ utility ─→ zoning ─→ population ─→ employment ─→ services ─→ finance ─→ traffic
                     ↑            ↑              ↑             ↑            ↑
                     └── 反向读一律取上月值（R24），用 Bus.TryGetLagged()

四、维护

  • 卡由拥有者维护（谁改契约谁改卡）。
  • 每次 decisions.md 新增涉及系统归属/接口的裁定，同一次提交里改对应卡。
  • 2026-11-22 首版 8 张，内容对应 R24–R32 之后的状态。
