v2 推进规划 · 按批次

📌 涉及性能取舍时，结论统一登记在 docs/design/19-tradeoffs.md；本文只说明"要什么"，不重复决定"砍什么"。
一批 = 一个能演示的东西 + 一条能跑命令的验收 + 一个不许跳的停止条件。
三样缺任何一样，就不算"一批"，只是一堆改动。
排期对齐 design/01-playable-definition.md §六 的四季度倒推；本文件把它拆成可执行的批次。
本文件是活文档，每批完成后改勾选并在文末签日期。

一、为什么会"盲目指挥"

用户 2026-11-15 原话：「刚做的时候我还犯了个错误就是盲目指挥导致后面就乱了」。 v1 的 04-collaboration.md §一 把这件事拆成过四条根因，v2 直接继承：

症状根因v2 的对策
两个代理先后改装配文件，一合并就丢东西共享文件被多方写装配只由 core/sim.cs 改，其它系统只交子场景
A 系统改了字段名，B 系统运行时才崩系统之间直接 get_node跨系统只走 bus（宪法 L3）
每个系统都往同一个文件里加两行没有所有权边界目录级所有权（宪法 L1）
谁都说"我的跑通了"，合起来不对没有统一验收每批一条可执行验收，不过不签收

但 v2 还要补第四条 v1 没有的：批次顺序。 v1 的乱有一半不是并行造成的，是下游系统建立在上游还没验收的东西上。 所以本文件的核心不是"分工"，是"什么顺序、什么时候停"。

⚠ "能浅 / 绝不能浅"（R34 第 5 条）：

  • 能浅：路网类型、建筑原型、服务种类、UI 面板（加类型不用改架构）
  • 绝不能浅：road_data 的 SoA 布局与围合面生成（B2，6 个系统全依赖）、

parcel 数据结构、Tick 顺序、bus 契约、存档格式 —— 一改就全线返工

⚠ 别把"B2 只直路/曲线"理解成 B2 可以做浅：V0 少的只是道路类型数量（不做高架/立交/桥）， 而 SoA 布局、围合面生成、路段拆分 必须一次做对——它们是下游 6 个系统的地基。

⚠ 每片结束必须"回填"（16 §5.4）：把为快而浅的实现换成正式实现，不是往上堆功能。

⚠ 从 V0 起分主档/试验档：主档干净给宣传片用，试验档随便玩。成本极低，别省。

B1 · 骨架

输入：B0 完成 ✅（2026-11-16）

⚠ 语言分工（decisions.md R19，2026-11-17）：
scripts/sim/ 与 core/ 用 C#（.cs），view/ ui/ tools/ 用 GDScript（.gd）。
依据 11-scale §6.4 实测：GDScript 做 15 万 agent 要 43 ms、1000 万月结要 3.1 秒，C# 是 ~25 ms 与 71 ms。
⇒ 项目必须开 mono；sim 改动要 dotnet build（几秒），迭代慢于 GDScript。
三条硬约束：禁 Vector3（用 float[]）/ MultiMesh 用 Buffer 批量 / 跨语言只传整块数组。
⚠ R32（2026-11-22）：语言不换成 Rust——C# 月结 71 ms / 预算 400 ms，余量 5.6×。
Rust 只在三条门槛全过时局部下沉（cdylib+P/Invoke），不进每帧路径。

目标：一个"什么都没有但什么都能接上去"的壳。不实现任何业务逻辑。

验收（四条）：

#断言

依据是"GDScript 月结约 10 s"的估算；实测（11-scale §6.4.1）C# 月结 71 ms / 预算 400 ms。

四、批次纪律（五条，缺一条就会重蹈 v1）

  1. 一批一个 tag：v0.1-b0 … v0.1-b7。tag 之间的 diff 就是这一批的全部内容
  2. 一批一段视频：30 秒，录不出来 = 这批没完成。"代码写了但没接起来"不算
  3. 验收不过不签收：不许"先合进来，下一批修"
  4. 不许跨批：B2 没验收就开 B3，等于把房子盖在没验收的地基上
  5. 每批结束改本文件的勾选 + 签日期
  6. 测什么用什么跑（2026-11-22 新增，见下表）——measurement 用错模式，等于没测

测量纪律：什么时候用无头，什么时候必须开窗

要证明的事用什么跑为什么
时间推进 / 月边界 / 闰年 / 日历 / 农历✅ --headless 或纯 .NET纯数值，不碰 GPU
存档往返 / 版本迁移 / 数据契约✅ --headless无渲染、无输入
系统顺序 / bus 读写 / 降级规则✅ --headless逻辑
CI 上"逻辑没退化"✅ --headless（CI 就该这么跑）无显卡也能跑，几十秒出结果
帧率 / 单帧预算 / draw call / 填充耗时❌ 必须开窗headless 不建渲染器、不提交 draw call、不等 GPU，测出来的数无效
画面正确性（LOD 切换、闪烁、z-fighting）❌ 必须开窗 + 截图只有窗口有画面
输入手感（相机、刷子、拖拽）❌ 必须开窗手动手感的唯一判据是人

⚠ 硬规则：任何写进文档的 FPS / ms 数字，必须注明是"开窗"还是"headless"。 只写"测得 60 fps"而不说是哪种，三个月后没人知道它能不能信。 ⚠ 空场景的帧率不算数：B1-1 的 ≥60 fps 要在地形与相机就位后测；B3 之后再测一次有建筑的。

五、派活前必须回答的七问（防"盲目指挥"）

给任何 AI 工具（含子代理）派活前，七个问题缺一个就会乱：

#问题不回答的后果
1你只能写哪个目录？它会顺手改你的基类
2你依赖谁的什么数据？走哪个 bus key？它自己造一套，和你并行造的另一套打架
3你的验收命令是什么？它说"跑通了"，你不知道通没通
4你要产出哪些文件？精确到文件名它会新建一堆你没规划的文件（v1 的 ui 目录 27 个文件就这么来的）
5你不许碰什么？它会"顺便优化"别人的代码
6完成后报告什么？你无法判断能不能合
7你和谁共享契约？（要动哪个 bus key / 结构字段 / 断言，谁受影响）并行时两套字段对不上，运行期才崩（agents.md §二·六）

反面例子（v1 犯过的）：

❌「帮我做一个住房系统」← 六问全缺，产出一定是缝合怪

正面例子：

✅「只写 scripts/sim/population/ 下三个文件 population_system.cs household.cs migration.cs。
先读 docs/contracts/population.md（契约卡）+ zoning.md（上游）+ 09-core-tick §7.4（别重造 core）。
依赖：bus 的 zoning.buildings（住房容量）、traffic.avg_commute_s（上月值，R24）与 config/sim/population.json。
产出文件仅这三个。不许碰 core/、zoning/、ui/。
契约：不改任何 bus key / 结构字段；如必须改，先停下来提裁定。
验收：godot --headless --script tools/acceptance.gd -- --case=population，要求 PP1–PP15 全绿并打印人口与容量。
报告：探针输出原文 + 接口变更（没改就写"无"） + 未完成项 + 需要协调者做什么。」

六、并行度上限

情况上限理由
默认1 个（串行）单人 + AI 的瓶颈是集成，不是产出速度
B4 / B62 个这两个批次内部有真正独立的子任务
任何批次不超过 3 个超过就变成互相等（v1 已验证）

⚠ 并行不是效率手段，是风险手段。 只有在"两个任务改的文件完全不重叠且不互相等"时才开。
