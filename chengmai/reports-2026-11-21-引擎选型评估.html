2026-11-21 引擎选型评估：Godot 能否胜任？要不要考虑 Unity / 虚幻？

触发：开发者提问「Godot 能否胜任？Unity 和虚幻引擎是否需要考虑？」
结论先行：继续用 Godot 4.7 mono。 但要守住三条硬约束，并在 B5 结束设一道复核闸门。
⚠ 本文是评估，不是裁定。要不要换引擎由开发者拍板（宪法 §五）。

一、先看清"胜任"到底在问什么

这个项目的负载有四块，只有一块和引擎强相关：

#负载量级和引擎的关系
①模拟（人口/就业/财政/OD）1000 万条数据、月结 71 ms（C#）几乎无关。只要语言能跑纯数组 + 不碰引擎 API，Godot / Unity / 自研都一样
②实例填充（把 agent 位置写进 MultiMesh）25 万实例 ≈ 13.7 ms（C# + Buffer）中。取决于引擎的批量 API。Godot MultiMesh.Buffer 已实测可用
③渲染提交（draw call）5–15 万栋建筑 + 15 万车（分块 + 4 档 LOD）强。这是唯一"换引擎可能变好"的一块
④世界流式（2500 km²、2500 瓦片）≤120 片激活强，但我们已经自己做了。引擎内建的流式（Unity Addressables / UE World Partition）能省事，不是必需

⚠ 关键判断：这个项目最难的 ①②④ 都和引擎无关。 换引擎能改善的只有 ③，而 ③ 目前 15 万 agent ≈ 25 ms（40 fps）、过了 30 fps 线， 不构成换引擎的理由。

二、三个引擎对这张需求表的正面回答

事实核对时间：2026-11-21。Godot 最新稳定为 4.7.2（4.8 在 beta）； Unity 为 Unity 6（运行时费用已于 2024 年取消）；Unreal 为 UE5.x。

需求Godot 4.7 monoUnity 6Unreal 5
主语言C#（.NET 8）+ GDScriptC#C++ + Blueprint
纯数组模拟性能实测 44× GDScript（bench/），够用Burst/DOTS 可再快数倍，但要重写架构C++ 快，但开发速度慢一个量级
海量实例MultiMesh + Buffer（已实测 5.49 ms/10 万）GPU Instancing / DOTS GraphicsNanite 只解决静态网格，动态车流仍需 Instancing
大世界流式❌ 无内建，必须自己按瓦片管（我们已设计）✅ Addressables / Scene streaming✅ World Partition（最强）
画面上限中（Forward+/SDFGI，够用）中高（HDRP）最高（Nanite + Lumen）
C# 在引擎里的成熟度✅ 桌面/移动可用；⚠ Web 导出仍是实验性；⚠ 主机需第三方移植✅ 最成熟❌ 无 C#（有第三方插件，不建议）
迭代速度⭐ 最快（编辑器秒开、C# 热重载部分可用）中（域重载慢，可关）慢（C++ 编译 + 编辑器重）
许可成本MIT，永久免费，零抽成年收入 ≤ 20 万美元免费；Pro ≈ 2,310 美元/席/年免费，单品终身收入超 100 万美元后抽 5%（EGS 渠道 3.5%）
单人 + 一年工期✅ 可行⚠ 可行但要先学 DOTS❌ 不现实

来源：Godot 官网下载页 / 4.7 迁移文档；Godot 4 in 2026 综述（C# 桌面可用、Web 实验性、大世界流式与会话级渲染是短板）； Unity 与 Unreal 定价对比（2026-10 核对：Unity 运行时费用已取消、Pro ≈ \$2,310/席/年；UE 5% 抽成门槛 100 万美元）。

三、为什么"不换"是理性选择（四条硬理由）

3.1 换引擎解决不了最难的部分

难的是 "1000 万人口 + OD 聚合 + 2500 km² 瓦片流式"这套架构，它由 11-scale 定，和引擎无关。 换到 Unity，这套架构一行不少写；换到 Unreal，还要用 C++ 再写一遍。

3.2 现有实测数据会全部作废

11-scale §6.4 那 30 多个数字（44×、71 ms、5.49 ms、13.7 ms、40 fps）是本机 + Godot 4.7 mono 测出来的。 换引擎后这些数字全部失效，等于把"用实测替代估算"这条路重新走一遍 —— 而那正是 R19 的依据。

3.3 单人 + 高考后一年，学习成本是最大的隐形成本

  • Unity：语言同是 C#，迁移成本最低；但要用 DOTS/Burst 补 CPU，等于再学一套范式，且 DOTS 生态坑多。
  • Unreal：C++ + Blueprint + 编辑器工作流，从零到能改引擎层至少 3–6 个月，直接吃掉可玩版工期。

3.4 许可与抽成

Godot MIT 零抽成；UE 抽 5%（100 万美元后）；Unity 订阅制。 对一个"可能是人生第一款商业作品"的项目，零抽成 + 零法务风险本身就是价值。

四、Godot 上必须守住的五条（否则会真的"不胜任"）

#约束违反的后果现在是否已守
E1模拟层不碰引擎 API（只跑 float[]/int[]）C# 的 interop 把优势吃光，退回 GDScript 量级✅ 宪法 §四 + L6
E2所有实例走 MultiMesh 分块（按 archetype × 2 km 区块），禁逐建筑 Node3Ddraw call 爆炸，5 万栋楼就掉到 20 fps✅ plan B3 停止条件已写
E3世界坐标用"浮动原点"：渲染时以当前瓦片为原点，避免 50 km 处 float32 精度抖动远景 z-fighting / 阴影抖⚠ 尚未写进文档，建议补
E4自建资产管线（R3），不指望 Asset StoreGodot 商店体量小，但本项目本来就自建✅ R3
E5不做 Web、不做主机（C# Web 导出仍实验性；主机需第三方移植）只做 Steam 桌面，风险归零✅ 无此需求

⚠ E3 是唯一一条"现在没写、以后会疼"的。建议写进 11-scale §十 或 10-presentation：

渲染层以"当前激活瓦片中心"为原点做坐标平移，sim/ 仍存绝对分米坐标。
50 km 处 float32 分辨率约 4 mm，静态建筑无感，但薄片（雨棚、桥面、车道线）会闪。

四·五、⭐ 城脉要"画质"，这条不能只靠引擎（2026-11-22 补）

开发者：「城脉也是需要追求一些画质的，虽然虚幻有 lumen，但是虚幻的游戏再加上 C++ 会很难优化。」

这两句都对，而且第二句正好点中换 UE 的真实代价。

4.5.1 先说清"城脉的画质"是什么

城建游戏的"好看"不是材质分辨率。四件事按重要性排：

#观感来源靠什么实现引擎相关度
1密度与体量（高楼群、天际线、街区肌理）街区尺度 + 容积率 + LOD + 分块合批低（这是设计 + 数据的事）
2车流/人流的存在感（城市是活的）15 万实例 + impostor 远景 + 车灯中（MultiMesh 批量写，已实测）
3光照与时间（黄昏、夜景招牌、窗光、雾）HDR + SSAO/SSIL + 体积雾 + 发光材质 + 昼夜相位高（Godot 4.7 已支持 HDR 输出）
4一致性（低饱和、克制的 UI、不花）10-presentation §四 的设计纪律无

⚠ 结论：占分最多的是第 1 条，而第 1 条是"密度 × 尺度"，不是"每块砖多精细"。 CS1 到今天仍然"好看"，靠的也不是材质，是楼群的高低错落与灯火密度。

4.5.2 Godot 4.7 在画质上能给到什么

能力状态对本项目
HDR 输出4.7 起支持（Win/macOS/Linux/iOS）✅ 夜景霓虹与车灯不过曝，这是"中国城市夜景"的前提
SDFGI / SSAO / SSIL / SSR4.x 内建✅ 够用；远景靠 SDFGI，近景靠 SSAO
体积雾 + 高度雾内建✅ 长江/雾都/晨雾，成本极低、观感提升大
区域光（AreaLight3D）4.7 新增✅ 招牌、店面、站台灯箱
TAA / FXAA / MSAA内建✅ 远景细线（车道线、栏杆）不闪
后处理（色调映射 / 辉光 / 景深）内建✅ 撑起"摄影感"，10-presentation §7.5 拍摄模式直接吃这个
Nanite 级虚拟几何❌ 没有⚠ 不需要：建筑是 26 类原型 × 模块，不是百万面扫描件
Lumen 级动态 GI❌ 质量不及⚠ 城市昼夜固定切换，烘焙 + SDFGI 混合足够，不需要每帧重算全局光

⚠ 没有 Nanite / Lumen 不等于"画质差"，只等于"不能走写实扫描资产的路线"。 而 R3 已经定了自建资产、低面数模块化——这条路本来就不吃 Nanite。

4.5.3 为什么"UE + C++ 难优化"是真的

项UE5Godot 4.7
自定义模拟系统的位置要么塞进 Actor/Component（跟引擎 Tick 与 GC 搏斗），要么写 UObject 生命周期Sim 层是纯 C# 数组，根本不在引擎里跑（宪法 §四）
迭代速度C++ 编译 + 编辑器热重载不稳，一次改动分钟级改完即跑；C# 侧 dotnet build 秒级
能不能改引擎❌ 源码可看但改引擎 = 自己维护一个分支✅ MIT，可改、可裁、可嵌
性能归因黑盒多（GC、Tick 分组、蓝图 VM），卡了不好定位三层清楚：logic（C#）/ fill（interop）/ render（GPU）——11-scale §6.4.5 已分开测过
本项目真正的瓶颈15 万 agent 推进 + 25 万实例填充同左，且已验证 C# 能压在 25 ms

⭐ 一句话：UE 的优化难点不在"UE 慢"，在"慢的时候你不知道慢在哪，而且改不动"。 我们这套架构恰好把"慢在哪"拆成了三个可独立测量的量——这是换 UE 会丢掉的资产。

4.5.4 所以画质怎么"追"（不换引擎的前提下）

杠杆做法成本
天际线容积率 + code_era 决定的高低错落；10-presentation §五 的 26 类原型按年代分层设计已定
夜景HDR + 发光材质（招牌/窗/车灯）+ 体积雾；车灯用 shader 而非光源低
密度感15 万真 agent（近景）+ impostor（中远景）+ 流量热力（远景）已设计
细节克制材质 ≤8、图集 2×4096、低饱和；不做每栋楼独立贴图已定（AR 断言）
拍摄模式慢镜头 + 隐藏 UI + 景深 + 10x 回放，产出短视频素材已设计（CAM1–CAM7）

⚠ 画质的验收不该是"像不像照片"，而是"截图能不能直接发"： 10-presentation AR 组断言 + 一个可执行的补充判据—— "同种子同一机位，截图与原画 1:1 对比，能数出窗格、招牌、车道线与行道树"（近景）， "远景能看出 3 种以上屋顶类型与 2 处以上地标"。这条建议加到 AR6/AR7。

五、什么情况下应该真的换（复核闸门）

时点：B5 结束（那时有真实帧预算，也有 15 万 agent 的成品）。

触发条件该换到说明
① 渲染提交 > 10 ms 且无法再分块/降 LOD，画面达不到"值得截图"的门槛Unity（HDRP）只有这一条是"引擎限制"，且要先穷尽分块与 LOD
② 美术方向改成"接近写实"（Nanite/Lumen 级材质与光照）Unreal⚠ "要画质"不等于"要写实"：密度、灯火、天际线在 Godot 就能做到；只有当目标是扫描级建筑 + 影视级 GI 时，UE 才真的赢（但成本翻倍、优化变黑盒）
③ 要上主机 / 要做 Web 版Unity / UnrealGodot 主机需第三方移植；C# Web 导出实验性
④ 需要成熟的第三方中间件（大规模植被、地形编辑、道路工具）UnityGodot 生态确实小

⚠ 除这四条之外，不建议换。尤其不要因为"Unity 教程多""Unreal 画面好"而换 —— 那两条对这个项目的瓶颈（每帧 15 万实例 + 月度 1000 万结算）都没有帮助。

六、如果现在就要一个"保险"

不做引擎切换，做"可迁移性"（成本几乎为零，且本来就在做）：

  1. sim/ 全部纯 C#、零引擎类型 → 换引擎时这 29 个文件可以整包搬
  2. 数据契约全走 config/*.json + FORMAT_VERSION 存档 → 不绑引擎序列化
  3. view/ 保持"薄"：只做"读 bus → 写 MultiMesh/材质" → 换引擎只重写这一层
  4. bench/ 保留原始代码 → 换引擎后能立刻重跑同一组基准做对比

⇒ 按现在的分层，真要换，代价是"重写 view/ + ui/"，不是"重写整个游戏"。 这就是宪法 §四"模拟层不认识引擎"的额外红利。
