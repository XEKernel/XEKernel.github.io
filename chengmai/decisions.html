Q1 · R1 路网密度 / R2 土地财政 / R3 学区，三条是否成立

背景 01-playable-definition.md §四 把 v1 的 14 条中国特色收敛到 3 条，作为核心循环（§4.2）的载体。 它们不是三个功能，是同一条因果链的三个环节：铺路 → 可达性↑ → 地价↑ → 卖地得钱 → 建学校 → 学区↑ → 地价↑↑。 若三条不成立，02–10 八篇设计文档的靶子全部落空。

候选

方案内容后果
AR1 + R2 + R3 全立B6 交付 3 个 .gd + 2 个面板；A3/A4/A5/A6 四条断言全部有对应实现；8 个系统全部有事干
B只立 R1 + R2，学校推到打磨年B6 减负约 1/3，services/ 降为单文件；但 A5 断言作废，P4「成长质变」少一个杠杆，循环缺正反馈加速器
C只立 R2 土地财政循环退化成纯卖地游戏；A3（R1 生效）作废，B2 路网失去设计理由，只剩「能画线」
D三条全否，另定循环02–10 需整体重写，B0 回到零，工期 +2~3 月

AI 建议：A，但 R3 用最小实现。 理由：R3 的真实成本不在机制，在于容易写成「教师-生源-设施」三本账（v1 就是这么膨胀的）。 最小实现 = 一个标量评分 + 半径衰减函数（school_score = f(投入) × exp(-dist/500m)）， 不建账本、不做教师个体。这样 A5 可测，成本可控在 1 个文件内。

⚠ 2026-11-15 复查补注（不改本条结论，只补一个漏项）：
R2 目前只有「卖」，没有「收」。地是凭空出现的。真实的土地财政是
收储（拆迁补偿）→ 一级开发 → 招拍挂 → 出让，中间有一大块成本。
缺这一环的直接后果是 A6 断言会假绿 —— 成本项少一半，「只收税当然容易亏」这个结论不再有力。
拍板 Q1 时请一并明确：拆迁收储是进可玩版，还是用「地块默认已收储」简化掉。
详见 reports/2026-11-15-缺口审查.md §2.2 F5。

R21 · 采用 ECS 的"数据布局与句柄机制"，不采用完整 ECS 框架

  • 裁定人：开发者
  • 日期：2026-11-18
  • 原话：「我们城脉要使用 ECS，不然后面硬件开销太大」
  • 依据：CS1 逆向源码实测（docs/reference/cs1-decomp-notes.md）

⭐ 先说一个必须知道的事实：

CS1 根本不是 ECS，它是 Manager + 手写句柄池（Array16/Array32）。
CS2 才是真 ECS（Unity DOTS），而 CS2 发售后性能翻车。

⇒ 所以"用 ECS 降低硬件开销"这个前提部分不成立： 降开销的不是 ECS 的框架，是它的数据布局。

三层拆分（这是本裁定的核心）：

层内容采纳理由
① 数据布局SoA / 结构体数组，组件按列存✅ 已在做缓存友好，这是性能的真正来源
② 句柄机制固定容量预分配 + 稳定索引 ID + 空闲槽复用✅ 采纳（学 CS1 Array32）零 GC、可存档、引用不失效
③ 完整 ECS 框架运行时动态组件组合 / archetype 迁移 / 系统调度器❌ 不做见下

为什么不做 ③：

理由说明
实体类型是固定的我们只有 8 类：citizen household vehicle building parcel agent district link。不需要运行时动态加删组件
archetype 迁移是最大开销加/删组件会触发数据搬移。我们一个实体从头到尾字段不变，根本不会有迁移
间接寻址反而更慢ECS 的 entity → archetype → chunk → component 多跳寻址，比直接 array[i] 慢
CS2 是反面证据同样的规模，DOTS 没跑过 CS1 的手写句柄池

⚠ 不采纳 ③ 不代表"不用 ECS 的思想"：①② 就是 ECS 的精华，我们全拿。 只是不引入第三方 ECS 框架的运行时开销。

具体落地（改哪几处）：

项现状改后
人口数组PackedByteArray 等 Godot 容器Array32&lt;T&gt; 式句柄池（固定容量 + uint 索引 + 空闲栈）
索引类型混用一律 uint，禁用 ushort（65536 上限的来源）
户的成员未定内联槽，但槽数与类型放宽（CS1 是 5 个 uint）
容量动态按上限一次预分配，不扩容（扩容=引用失效）
存档存数组内容同 CS1：索引就是 ID，存档=数组快照

⚠ 如果将来发现某一块真的需要动态组件（比如可插拔的 DLC 机制）， 只在那一个系统内局部使用 ECS 模式，不做全局改造。

与 R19（C#）的关系：句柄池用 C# 实现（sim/ 已是 C#）。 C# 的 struct[] + uint 索引，就是 CS1 在 .NET 里做的事，性能已经被验证过。

R35 · 做车道级连接（推翻 R 前身 §3.6.5b 的"不做"）

  • 裁定人：开发者（2026-11-25）
  • 原话：「车道级连接我觉得可以做一下，毕竟高自由度也是这个游戏的特点。」
  • 推翻的是：design/02-road.md §3.6.5b（2026-11-18 定「不做车道级连接」）

与 design/08-traffic.md §3.6.3 表里的"路口内车道连接 = 不做"。

  • 背景与重新评估：
  • 2026-11-18 的判断是「OD 聚合下车道细节对宏观流量没贡献，却要一个子系统」。
  • 但我漏了一件已经存在的事：08 §3.6.2 已经定「agent 生成时按 OD 方向定车道归属」

（左转靠左 / 右转靠右 / 直行居中）。也就是说车已经在正确的车道上了， 缺的只是路口内那一段的连接关系。

  • 因此这不是"从零做车道图"，而是"给已有的车道归属补上路口内的走向"。代价比原估低一个量级。
  • 另有三个视觉收益是原判断低估的：① 标线导向箭头能对上车道（否则箭头与车流不符，很假）；

② 多方向同时右转不会在路口中心打结；③ 为左转待转区 / 可变车道 / 潮汐车道留接口 （这三样是中国城市的真实特征，12-china-features 有登记）。

  • 裁定：分四级，只做 Lv0–Lv2，Lv3 仍不做。
级内容做不做代价
Lv0车道归属（生成时按转向定一次 + 抖动）✅ 已有（08 §3.6.2）0
Lv1转向车道配置：每个进口方向指定几条左转/直行/右转道✅ 必做低（3 个数字）
Lv2路口内车道连接：进口道 → 出口道的对应关系✅ 做中（弧线生成 + 数据结构）
Lv3段内逐车变道（MOBIL 类）❌ 不做高（与代表性 agent 冲突）
  • ⭐ 关键实现约束（决定代价可控）：

lane_links 由规则推导，不存全量图；只存玩家覆盖值。

项做法
默认连接按转向类型 + 车道位置推导（左转：最左 n 道 → 对向最左 n 道；右转：最右 n 道 → 最右 n 道；直行：同位对应）
玩家覆盖只在自由档可以改；覆盖值进存档（与 §3.10.14 标线推导同一套思路）
弧线路口内用 Bezier 生成，按"车道中心线"求出入口/出口切线；不存采样点，进表现层
规模若全量存：4 进口 × 4 道 × 3 向 ≈ 48 条/路口 × 数万路口 = 百万级。推导后只存覆盖，通常为 0
  • 影响：
  • 02-road §3.6.5b 整节重写为"做，但分层"；新增 node.lane_links_override（稀疏，默认空）
  • 08-traffic §3.6.3 的三层表改：路口连接「不做 → Lv2 做」；§3.6.2 的车道归属不变
  • B2 要预留接口（node 结构里留覆盖字段，B2 不实现连接生成）
  • B5 的范围扩大：要包含 Lv1 转向配置 + Lv2 弧线生成 + 车道级排队形态
  • 存档：加稀疏覆盖字段 ⇒ FORMAT_VERSION 再 +1（与 §3.10 的 corridor 一起，3 → 4 或 5）
  • ⚠ 验收要新增"车道级"断言（见 02-road §3.6.5b 的 RD-L1~L3）
  • 明确不做（防膨胀）：
  • 段内逐车变道（Lv3）——维持"生成时定 + 抖动"
