二、三层模型（千万人口能跑的唯一结构）

① 需求层  OD 矩阵        2500 个交通小区（TA，1 km²）→ 非零 OD 对约 50–80 万
            ↓ 月边界算一次
② 流量层  时段分配       同一份 OD × 4 个时段系数 → 4 次分配 → 4 份路段流量表
            ↓ 输出：每条路段的饱和度 / 速度 / 行程时间
③ 表现层  代表性 agent   车辆 ≤ 20 万、行人 ≤ 5 万（从流量表抽样）

为什么必须这样：1000 万人 × 2 次出行/日 = 2000 万次。 1 游戏日 = 3 秒 ⇒ 需 667 万次寻路/秒，每次 3 μs 就是 2000 % 单核。 ⇒ 逐人寻路不是"慢"，是复杂度上不可能（11-scale.md §1.2 有完整测算）。

同一对 OD 的 1000 个人走同一条路 —— 这不是偷懒，是交通规划六十年的标准做法 （TransCAD / EMME 都这么算），也是 CS1 只需要 65,536 个 agent 的真实原因。

三、双层流量：宏观全量 + 微观代表

层规模参与数值参与渲染
宏观（路段流量）全量：15 万段 × 4 时段✅ 决定拥堵度、行程时间、地价影响❌（用热力/着色表达）
微观（车辆 agent）≤ 20 万（U4），活跃 ≤ 15 万（U3，R5 签收）❌✅

⚠ 这是最容易搞错的一处：宏观层才是"真值"，微观 agent 只是让它看得见。 删掉全部 agent，拥堵度、通勤时间、地价一分不变（R2 相机边界的直接推论）。

三·五、多方式 OD：地铁与公交怎么接进来（R18）

地铁回归本体之后，OD 不再只有"开车"一种方式。
⚠ 这里有一个决定成本的关键取舍，先说清楚。

3.5.1 地铁不做车辆 agent，只做"分流"

做法成本采纳
挖隧道 + 地铁车跑 agent + 站内换乘动线极高（等于再做半个交通系统）❌
只做"运力分流"：一部分 OD 转走轨道，不生成车低（流量分配多一条方式）✅

⚠ 地铁在游戏里的价值是"分流 OD"，不是"开地铁看车跑"。 玩家的决策是"修这条线能不能缓解这条主干道的拥堵"，而不是"看地铁准不准点"。 ⇒ 画面用车站 + 地面出入口表达（地下不显示，CS1 也这么干）。

3.5.2 方式分担模型

对每一对 OD：
  1. 步行/骑行可达（< 1.5 km）        → 非机动（占用骑手/行人通道，不影响机动车流量）
  2. 轨道可达（起点 800 m + 终点 800 m 内有站）→ 按轨道优势度决定分担率
  3. 其余                              → 走公路网（原有 flow_assign）
方式判定参数
walk/ebike距离 < 1.5 km固定比例
metro两端各有站点 ≤ 800 m 且无需换乘或换乘 ≤ 1 次分担率 = f(轨道时间 / 公路时间)
bus沿线有站，共享路网（占道路容量）分担率 = f(班次密度)
car其余全部—

⚠ bus 与 metro 的本质区别：公交占道路容量（会加剧拥堵），地铁不占。 这个区别必须在模型里体现，否则"建公交治堵"会变成真的治堵——那是错的。

3.5.3 轨道线路的数据结构（极简）

结构字段上限
metro_lineid stop_range(u32,u16) is_loop≤ 64 条
metro_stopid cell_x/y line_ids(2×u8) parcel_id≤ 2,000 站
metro_spanfrom_stop to_stop alignment(u8) length_dm cost≤ 4,000 段

⚠ 不做轨道几何（不存曲线、不存隧道）。站与站之间按"直线距离 × 绕行系数"算时间。 ⚠ 换乘上限 1 次：超过就退回公路。否则换乘搜索会吃掉整个分配预算。

3.5.4 三种敷设方式：地形说了算（2026-11-16 补充）

用户：「地铁有时候并不完全在地下，有时候受地形影响还是要到地面的。」

这条纠正了我上一轮"一律不建地上部分"的说法。 中国的"地铁"实际是城市轨道交通， 包含三种敷设方式，而且地形是主要决定因素。

敷设alignment造价系数占地噪音沿线地价典型场景
地下01.00无（只有出入口）无0平原市区、老城核心
高架10.60桥墩 + 声屏障有−10 %（200 m 内）跨江、软土、郊区、山地
地面20.35路基走廊有−15 %利用旧铁路、远郊

⭐ 地形第一次成为"交通成本"的变量（此前地形只影响水源与景观）：

地形条件强制/倾向
河流 / 湖泊 / 海湾跨江段必须高架或桥隧，造价 ×1.8
山体 / 陡坡（坡度 > 8 %）必须隧道或高架，地下段不能浅埋
软土地基（沿海）地下段造价 ×1.3（需加固）
平整平原（华北/长江中下游）默认全地下，最省事
旧铁路走廊地面段造价 ×0.6（可直接利用）

⚠ 这解释了重庆为什么是"8D 魔幻城市"：山地 + 两江，逼出大量高架与穿楼而过的站 （李子坝那个"轻轨穿楼"就是地形逼出来的结果，不是设计师的浪漫）。

⚠ 玩家会有真实的取舍：

  • 全地下 → 贵，但沿线不闹、地价不跌
  • 高架 → 便宜四成，但沿线居民会反对（接 F97 邻避），且地价跌
  • 地面 → 最便宜，但把城市切开（类似铁路的"割裂效应"）

⚠ 默认策略：生成时按地形自动推荐（平原→地下、跨江→高架、山地→高架/隧道）， 玩家可以改，但改了要付相应造价。

⚠ 视觉规则：

  • 地下段不建模（只画车站出入口 + 地图叠层显示线位）
  • 高架段建模：桥墩 + 轨道梁 + 声屏障（metro_viaduct 模块）
  • 地面段建模：路基 + 围栏 + 平交道口（metro_viaduct 复用地表形态）

3.5.5 工期：不能照搬现实

⚠ 现实地铁一条线要修 5 年 = 游戏 91 分钟（1x），玩家等不起。

做法结果
照搬现实（5 年）91 分钟没收益，玩家会以为功能坏了
压缩到 1–2 游戏年18–37 分钟，可接受
分段开通（每通一段就有收益）最好的做法：先通一段，玩家立刻看到分流效果

⇒ 采纳：工期 1–2 游戏年 + 分段开通。 ⚠ 这与"村庄 30 年变镇"是同一个道理：真实节奏在游戏里会杀死体验， 必须在"真实"与"可玩"之间做减法，并且明确知道自己在减什么。

3.5.6 对拥堵的反哺

地铁分流之后，公路网的流量下降 → 拥堵下降 → avg_commute_s 下降 → 地价上升。 这条闭环是"地铁一响黄金万两"在数值上的实现。

⚠ 但要注意：地铁修错地方（没有 OD 经过）会白花钱，还占财政。 这是玩家必须面对的真实决策。

三·六、⭐ 多路径分配：不重蹈 CS1 的"只走最近路"（2026-11-18 定）

用户：「CS1 有一个让人诟病的问题，就是只走最近的路，然后还只走一个车道。
虽然这在性能上是最好的优化，但是在模拟上是很糟糕的。」

这是必须避开的第一号问题。 它有两个层面，解法不同。

3.6.1 层面一：路径——不能 100 % 给最短路

❌ all-or-nothing 会出什么事

现象玩家看到
所有 OD 100 % 走最短路一条主干道堵死，旁边平行的路空着
玩家加宽那条路更堵（诱导需求），旁边还是空
玩家在平行路上修同样的路没人走（因为不是"最短"）

⚠ 这直接摧毁"规划"这个玩法：玩家做的所有分流都没有正反馈。

✅ 解法：增量分配 + Dial 似然分配

cost = 自由流成本（初始）

for k in 1..K:                        # K = 3~4 轮
    对每个起点 TA 跑一次 Dijkstra（分层路网）→ 得到最短路树 + 每节点 cost
    在该树上用 Dial 算法把 OD 量按似然分到多条合理路径
    按 BPR 函数更新路段 cost
环节作用
Dijkstra（分层）只跑 2500 次（每起点一次），不是每个 OD 对跑一次
Dial 似然分配在同一棵最短路树上把流量摊到多条路径，几乎不增加成本
增量 K 轮每轮用更新后的 cost 重算 ⇒ 拥堵会"推"车去别的路

⭐ 关键：多路径 ≠ 更慢。 Dial 算法在已经算好的最短路树上做分配，不需要额外求最短路。 成本增加几乎全部来自 K 轮迭代，不是来自"多路径"本身。

成本预算

项估算
一次全图 Dijkstra（分层，2500 起点）≈ 150–250 ms（C#）
× K=3 轮≈ 450–750 ms
4 时段超出原预算 800 ms ⚠

⇒ 取舍（三选一，B5 实测后定）：

方案成本真实度
K=3，4 时段全跑~3 s/月⚠ 需摊平到更多天
K=3，只跑 2 个高峰时段，平峰复用~1.5 s/月✅ 推荐（平峰差异小）
K=1 + Dial（只摊流量不迭代）~800 ms⚠ 拥堵不会"推"车改道

⚠ 推荐第二方案：早高峰 / 晚高峰各跑一次，平峰用早高峰的结果缩放。 平峰的路径选择与早高峰高度相似，省一半算力几乎无损。

3.6.2 层面二：车道——不能所有车都叠在中心线

CS1 的问题：车选一条车道就不换，导致一条车道排满、旁边车道空。

我们的做法（简化，不做逐车变道）

项做法
车道归属agent 生成时按 OD 方向定一次（左转靠左 / 右转靠右 / 直行居中）
横向位置车道号 × 车道宽 + 抖动，段内不变
变道❌ 不做
路口内按 OD 方向直接转（§3.6.5b）

⚠ "抖动"很重要：即使同车道，也不要在完全相同的横向坐标上—— 否则视角稍微斜一点就看出一串"穿在一起的塑料车"。

⚠ 不做变道是刻意的：逐车变道要维护"目标车道 + 相邻车道占用 + 换道时机"， 这是 CS1 花了很多代码做的事，而视觉收益很小。

3.6.3 ⭐ 三层"车道级细节"的取舍表

层CS1我们代价
路径选择最短路（all-or-nothing）多路径（Dial + 增量）+K 轮 Dijkstra
段内车道选定不变生成时定 + 抖动≈ 0
转向车道配置无此概念⭐ 有（n_l / n_s / n_r，02-road §3.6.5b Lv1）低（3 个数）
路口内车道连接逐车道⭐ 做（Lv2，2026-11-25 改，原为"不做"）中（Bezier + 稀疏覆盖）
段内逐车变道运行时不换道❌ 不做（Lv3）高（与代表性 agent 冲突）

⚠ 这张表 2026-11-25 改过：路口连接从"不做"改成"做"（R35）。 原来写"把算力花在路径上、省在车道"——后半句撤回：车道连接影响 标线一致性 / 多向右转是否打结 / 排队形态，这些都是玩家一眼能看出的， 不只是"微观细节"。

⚠ 但"省钱"的部分仍然成立：lane_links 由规则推导、只存覆盖（02-road §3.6.5b）， 所以是"做车道级观感"，不是"存一张百万级的车道图"。

⚠ 仍然不做的是"段内逐车变道"：维持"生成时定 + 抖动"， 因为逐车变道要维护车道级队列与相邻占用，那是逐车模拟的活（§3.6.2）。

3.6.4 ⭐ 广义成本：为什么"最近的路"不一定是"走的路"

用户：「在现实中每辆车的速度是不一样的，有的会超车等，假如看到前方堵车就知道要绕路，
或者其他因素并不会走最近的路（比如最近的路红绿灯多）。」

"红绿灯多"这条点出了一个缺项：我们原来只算了行驶时间 + 拥堵，没算交叉口。

广义成本 = 四项相加

cost(path) = Σ 自由流时间
           + Σ 拥堵延误(BPR)
           + Σ 交叉口延误          ← 2026-11-18 新增
           + Σ 转向惩罚
项取值说明
自由流时间长度 ÷ 限速已有
拥堵延误t0 × (1 + 0.15·(v/c)^4)已有（BPR）
交叉口延误直行 +8 s / 右转 +5 s / 左转 +15 s / 无信号 +3 s⭐ 新增
转向惩罚左转额外 +5 s，掉头 +20 s⭐ 新增

⚠ 不模拟红绿灯配时，只用每个路口的固定延误近似。 理由：配时是纯细节，加起来的总量才是玩家感知到的东西。

3.6.6 超车：占用率驱动的"能超就超、车多就排"

⚠ 本节 2026-11-18 修正过。 初版写的是"按速度分车道（快车内侧、慢车外侧）"，
这是错的。用户指出：「快车总会找机会超车，况且在市区内速度一般快不起来，
车少好超，但是车多就不好超，会选择绕路或者继续走，你说的慢车道和快车道是高速上的做法。」

完全正确。 "按速度分车道"是高速/快速路的规则（且靠法规维持）， 市区道路没有这种分工，超车是驾驶行为，不是车道规则。

真正的机制：超车需要"空隙"

能不能超 = f(该方向 / 对向的占用率)
占用率 v/c行为画面
< 0.4（车少）自由超越：快车横向错位越过慢车空旷路上有车来回穿
0.4 – 0.7（过渡）概率超越：按 (0.7 − v/c) / 0.3 决定偶尔超一下
> 0.7（车多）强制跟车：速度 = 该路段实际速度排队，谁也不能超

⭐ 这个模型自动产生了"车多就不好超"的效果——不需要额外的判断逻辑。

⭐ 关键：用"路段饱和"近似，不做逐车前车检测

逐车检测的代价：需要知道每条路段、每个车道上有哪些车、顺序如何， 每帧排序 = 15 万 × log(n) 的开销，还要维护车道级队列。

我们的近似（与"宏观分配 + 代表性 agent"的架构一致）：

输入来源成本
该方向 v/cflow_assign 已经算好了0
agent 的 speed_factor生成时定0
实际速度 = min(自身期望速度, 路段实际速度)
横向偏移 = 能超 ? (随机 ±半车道宽) : 0

⚠ min(自身, 路段实际速度) 是核心： 路段实际速度已经由 BPR 从 v/c 算出，它天然包含"车多就慢"。 ⇒ agent 只要不"超过路段整体速度"，宏观与微观就永远自洽。

⭐ 这比 CS1 的逐车模拟更省，而且更难出错： CS1 要维护车与车的跟驰关系，一旦参数调不好就出现"幽灵堵车"； 我们的速度直接由宏观饱和决定，不可能出现宏观说畅通、微观却排队的矛盾。

⚠ 市区里 speed_factor 的视觉价值比高速低

场景绝对速度差（0.85 vs 1.15）
高速 80 km/h24 km/h（很明显）
市区 40 km/h12 km/h（近景能看出，远看差不多）
拥堵 15 km/h4.5 km/h（几乎看不出）

⇒ speed_factor 仍然要，但它的主要价值是"不至于所有车完全同步"， 而不是制造肉眼可见的超车大戏。

⚠ 想要"超车大戏"，必须靠"占用率低时允许横向错位"（上表第一行）， 而不是靠加大速度差。

"车多时选择绕路"

⚠ 这是 en-route reroute，我们仍然不做（§3.6.7）。 玩家感知到的"堵了以后分流"由时段级增量分配提供。

3.6.7 "看到堵车就绕路"：不做逐车实时重路由

方案成本玩家能否感知

4.5.1 ⚠ MultiMesh.Buffer vs 逐个写入：取决于语言，且正好相反

语言更快的方式10 万实体实测50 万实体实测
GDScript逐个 set_instance_transform9.40 ms47.23 ms
GDScriptmm.buffer = buf（批量）50.26 ms ❌255.74 ms ❌
C#mm.Buffer = buf（批量）5.49 ms ✅29.33 ms ✅

⭐ 原因：

  • GDScript：每条语句都贵，批量要写 16 个 float/实例 = 16 条语句
  • C#：语句便宜，但 SetInstanceTransform 每次跨 C#/C++ 边界约 90 ns，

与 GDScript 的调用开销同量级 —— 换语言救不了

  • buffer 只有一次 interop，之后是引擎内部 memcpy

⚠ 规则（按最终语言二选一，不要两套都写）：

  • 若 traffic 用 C# → 必须用 Buffer 批量，禁用逐个 API
  • 若用 GDScript → 用逐个 API（但仍会超预算，见 §4.5.2）

用户指出「快车总会找机会超车，市区内速度一般快不起来，车少好超、车多不好超， 慢车道快车道是高速上的做法」。 改为 占用率驱动的超车模型：能不能超 = f(该方向 v/c)—— v/c &lt; 0.4 自由超越（横向错位）/ 0.4–0.7 概率超越 / &gt; 0.7 强制跟车。 ⭐ 核心规则 实际速度 = min(自身期望, 路段实际速度)： 路段实际速度已由 BPR 从 v/c 算出 ⇒ 宏观与微观永远自洽，不可能出现幽灵堵车。 ⚠ 不做逐车前车检测（那是 CS1 的成本与风险来源），只读 flow_assign 已算好的 v/c。 并说明 市区 speed_factor 的视觉价值低于高速（40km/h 下只差 12km/h）， 它的主要作用是"不至于所有车完全同步"。TR18 改为"车少能超 / 车多排队"，新增 TR19（速度上限自洽）。

「只走最近的路，还只走一个车道——性能好但模拟糟糕」： ① 路径层：不做 all-or-nothing，改 增量分配（K=3~4 轮）+ Dial 似然分配。 ⭐ 关键：多路径 ≠ 更慢 —— Dial 在已算好的最短路树上摊流量，不额外求最短路； 成本增加几乎全来自 K 轮迭代。 ⚠ 成本超原预算（4 时段全跑约 3 s）⇒ 推荐只跑早晚高峰、平峰复用（~1.5 s）。 ② 车道层：agent 生成时按 OD 方向定车道 + 横向抖动，不做变道（视觉收益小、成本高）。 ③ 定下核心取舍：把算力花在"路径"上，省在"车道"上——理由： 路径选择影响玩家决策，车道细节不影响。 新增 TR11–TR14 四条断言，其中 TR13（平行路分流有效，通勤降 15 %) 是本节的存在理由。 §九 待定第 1 条（增量 vs SUE）结案。
