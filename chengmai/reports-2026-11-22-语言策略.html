语言策略：C# 够不够？要不要 Rust / 混合？（2026-11-22）

触发：开发者「v1 是用 Rust，v2 文档改成 C#，Rust 效率更高也更安全，我在考虑到底用不用 Rust 或 C#+Rust 混合」。
结论：保持 R19（C# 为主），但把"什么时候允许下沉 Rust"写成三条可量化的门槛。
⚠ 本文是提案，不是裁定；要改 R19 需走宪法 §五。

一、先把"快多少"钉在数字上（本机实测，11-scale §6.4.1）

实现ns / 实体1000 万月结相对 GDScript
Rust 8 线程1.717 ms182×
Rust 单线程2.828 ms111×
C#（.NET 8, Release）7.171 ms44×
GDScript3103.1 s1×

预算 400 ms ⇒ C# 有 5.6 倍余量，Rust 有 23 倍。 两者都远在预算内，所以"Rust 更快"在当前规模上没有可感知的收益。

⚠ 但要诚实：8 线程 Rust 只比单线程快 1.65 倍（1.7 vs 2.8）——这台机器 DDR3 8.8 GB/s 已饱和。 ⇒ 换语言不如换数据布局（u8/u16 代替 f32、SoA、降低频率），这三条我们已经在做。

二、真正紧的不是"月结"，是"OD 分配"

项现值（C# 估算）预算余量
1000 万人口月结71 ms400 ms5.6×
OD 分配（K=3 × 2 高峰时段）≈ 1.5 s / 月800 ms已超 1.9×
4 时段全跑≈ 3 s / 月800 ms超 3.75×

⇒ 只有 OD 分配这一块在超预算，其它都宽松。 而 OD 分配的加速第一条不是换语言，是并行：2500 个起点互不依赖， C# 用 Parallel.For 跑 8 线程预期 ≈ 3–4 倍（1.5 s → 0.4 s），一行代码量级。

⚠ 顺序不能倒：先并行 → 再降频率（只跑两个高峰）→ 还超才谈 Rust。 先上 Rust 会掩盖"算法没并行"这个问题，以后想改成并行还得再拆一次。

三、Rust 的代价（这个项目具体要付什么）

#代价具体表现量级
1跨语言边界渲染层每帧要 25 万实例的位置。sim 在 Rust ⇒ 这批数据必须过 FFI；过不好，fill 那 13.7 ms 立刻翻倍高
2集成路径三选一，都有坑① gdext（godot-rust，第三方绑定，跟引擎版本有滞后）② 手写 GDExtension C ABI（繁琐）③ 静态库 + P/Invoke（最可控，但要自己设计 ABI）中高
3三套运行时调试GDScript + C# + Rust。崩在边界上时，堆栈跨三个运行时，单人 + 一年工期最怕这个高
4构建与迭代cargo build + 链接 + Godot 重载，比 dotnet build（秒级）慢；热重载基本没有中
5内存安全收益有限sim 层的 bug 绝大多数是逻辑错（月边界、索引语义），不是悬垂指针；C# 的 Span&lt;T&gt; + struct 数组 + 边界检查已覆盖绝大部分低

⭐ 一句话：Rust 的"更安全"在"内存安全"维度成立，但这个项目的风险不在那个维度。

四、混合方案对比（三个都能做，但只有一个值得）

方案做法好处代价评价
A · C# 全量现状（R19）一套语言、边界清晰、迭代快OD 分配要并行化✅ 默认
B · C# + Rust 局部内核纯计算热点（如 OD 分配、栅格扩散）做成 cdylib，C# 用 P/Invoke热点快 2–4 倍；边界只在"每月的数组"上，不碰每帧多一条工具链、要设计稳定 ABI✅ 只在 B 过不了预算时用
C · Rust 做整个 sim（GDExtension）所有系统用 Rust 写纯 Rust 一致性每帧数据都要过边界 + 三套运行时 + gdext 版本风险❌ 不推荐

⚠ 方案 C 是最坏组合：既付了 Rust 的学习与集成成本，又没避开"数据跨界"这个真正的瓶颈。

五、三条准入门槛（建议写进 decisions.md，替代"感觉需要 Rust"）

某模块要下沉 Rust，三条全过才允许：

#门槛判据不过怎么办
R-1实测真的超该模块实测 > 预算 2 倍，且已做过：Span&lt;T&gt; / 结构体 / 并行 / 降频 之后仍超继续优化 C#，不许"提前上 Rust 保险"
R-2纯计算，无回调输入输出都是数组；不调引擎、不持跨帧状态、不回调 C# 对象改成纯计算再谈（设计问题）
R-3边界成本 < 收益单次跨界数据 < 20 MB，且频率 ≤ 每日一次（绝不允许每帧）留在 C#（每帧跨界是死路）
现状核对：population 月结（71 ms / 400 ms）✅ 不必；traffic agent 推进（4.1 ms / 帧）❌ 违反 R-3；
OD 分配 ⚠ 满足 R-2/R-3，但先并行（预期 0.4 s，进预算）→ 大概率也不必下沉。

六、结论与理由（按重要性）

  1. Rust 解决的不是这个项目的瓶颈。 v1 用 Rust 也没救回来——v1 死在架构（逐人寻路、系统平铺），不是死在语言。
  2. C# 有 5.6 倍余量，唯一超预算的 OD 分配先并行就能进预算。
  3. 每帧跨界是死路：agent 与实例数据每帧都要过边界，Rust 在这里只增加风险不增加速度。
  4. 单人 + 高考后一年：三套运行时的调试成本 > 性能收益。这条最现实。
  5. 不锁死：sim/ 是纯 C# 数组，将来若真换 Unity 可以直接搬；若某块要下沉 Rust，走方案 B 即可。

建议的定案

保持 R19：sim/ + core/ 用 C#；Rust 只在"R-1/R-2/R-3 三条全过"时局部下沉（方案 B），且不进每帧路径。
同时把"OD 分配先并行"写成 B5 的第一条优化动作（在考虑任何 native 之前）。
