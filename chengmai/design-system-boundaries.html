一、一句话规则

数据由谁产生，就归谁所有。别人只能读，不能写。

跨系统的写只有一条合法路径：走 bus 的 key，由拥有者写、消费者读。 get_node("../Other").field = x 一律视为 bug（宪法 L3）。

⚠ 注册契约（2026-11-22 起，代码已强制）：每个系统的 ISimSystem.Name 必须等于本表 §二 的系统名 （road / utility / …），否则 Sim.Register 直接抛异常——这样"少一个系统/拼错名字"在启动时就会炸， 而不是在统计里悄悄少一个。

三、逐系统明细

1 · road — 唯一的空间来源

项内容
拥有lane_graph（节点/路段/车道，三级 + 快速路）<br>block_face（路网围合面，R6 要求）<br>道路等级 H / M / L / 支路<br>accessibility 场（R1 可达性）
读玩家编辑事件（画路/拆路）
写（bus）road.lanes · road.block_faces · road.accessibility
文件（≤3）road_graph.cs · block_face.cs · accessibility.cs
频率事件驱动（只在玩家改路时变）

⚠ block_face 是本系统的关键产出：没有它，zoning 没有对象可分区（11-scale.md §2.3）。 ⚠ **road 没有 *_system 文件（3 文件已排满）⇒ ISimSystem 实现（RoadSystem）落在 road_graph.cs 里， Cadence = Event，由 Sim.RaiseEvent("road") 调用。 ⚠ 围合面用半边结构/DCEL** 求，复杂度 O(E log E)，玩家画路时才跑，不在每 tick。

2 · utility — 市政（新增，R15）

项内容
拥有电力网络：杆塔（4 级）+ 链路 + 容量衰减 + 峰值负荷<br>供水链：抽水站（须临水体）→ 净水厂 → 泵房<br>污水：收集 → 处理厂（须在水体下游）→ 排放<br>雨水：管网容量 + 径流系数 + 内涝<br>通信：机房 → 基站覆盖<br>燃气：站 + 覆盖半径<br>垃圾：转运 → 焚烧/填埋<br>每件设施的 age 与 design_life（老化与故障）
读road.lanes（杆塔沿路布点）· zoning.parcels（需求与硬化率）· 地形水体
写（bus）utility.power_ok · utility.water_ok · utility.sewage_rate · utility.drain_ok · utility.comm_ok · utility.gas_ok · utility.waste_ok · utility.peak_load · utility.failure · utility.shortage
文件（≤3）utility_system.cs（框架/覆盖栅格/缺口分配）<br>power_grid.cs（图结构专管电力）<br>utility_chain.cs（水/污水/通信/燃气，链与点）
频率游戏月

⚠ 为什么 3 个文件能装下（此前担心要 7 个）： 电力是图，其余是链/点，两者无共享代码 → 各占一个文件；框架再一个。正好 3 个。

⚠ 2026-11-16 扩了五个子领域之后仍然成立（电力 / 供水链 / 污水 / 雨水 / 通信 / 燃气 / 垃圾 / 老化）： 它们全部是"链"或"点"结构，共用 utility_chain.cs 的框架， 只有电力是图，单独一个文件。老化与故障是"给每个设施加两个字段"，不增加文件。 ⚠ utility 必须在 zoning 之前算：容量决定地块能不能生长（宪法 §三）。

3 · zoning — 城市的形状

项内容
拥有parcel（多边形 + use_code + far + density + height_limit + code_era + land_value 缓存）<br>compound（小区：基坑/车位/覆土/社区用房/四阶段/分期）<br>building（archetype + floors + level + state）<br>建材需求量（在建面积 × 单位消耗）
读road.block_faces · road.accessibility · utility.*_ok · population.demand（上月值） · employment.demand（上月值） · employment.last_month_output（上月值） · finance.land_value（上月值）
写（bus）zoning.parcels · zoning.buildings · zoning.material_demand · zoning.pollution（预留 DLC2）· zoning.unplanned（预留 DLC3）
文件（≤3）zoning_system.cs · parcel_subdiv.cs（沿街面宽细分 + 五种布局原型生成建筑） · growth.cs（生长/升级/废弃）
频率游戏日（growth）+ 月（需求汇总）

⚠ zoning 读 employment 上月产能（建材）是"反向读"的第一个例子，不是唯一一个（R24 已把规则通用化）。 理由：建材供给决定建设速度，而 employment 按 Tick 顺序在 zoning 之后。 用滞后一期解决，而不是改 Tick 顺序。 这条是特例，其他地方一律禁止反向读。

四、依赖方向（谁读谁）

road ──┬─→ utility ─→ zoning ──┬─→ population ──┬─→ employment ──┬─→ services ─→ finance ─→ traffic
       │                       │                │                │
       └───────────────────────┴────────────────┴────────────────┴──────────────→ traffic

硬规则：

⚠ 2026-11-21 依 R24 改写：原写"唯一的反向读是 zoning 读 employment 上月产能"——
但 §三 明细里实际有 5 处反向读。规则已改，不是特例，是通用做法。
规则说明
优先读 Tick 顺序在自己之前的系统同帧最新值，无延迟
读 Tick 顺序之后的系统 ⇒ 一律读「上月值」，并标 stale（R24）五个系统不受顺序限制，代价是数据晚一个月。实现就是 §四·五 的降级机制，不需要新概念
traffic 是唯一读 clock.time_slot 的系统其他系统读它一律违规（09-core-tick §七）

⚠ 为什么不是"调整 Tick 顺序"：finance 的地价要靠人口与就业，traffic 的通勤要靠人口与路网—— 顺序怎么排都会有环。用"滞后一期"断环，是唯一不需要发明新机制的解法。

四·五、数据缺失时的降级规则（2026-11-17 补）

系统间耦合最容易出问题的地方：上游这个月没算出东西，下游读什么？
不定义这条，每个系统都会自己编一个默认值，最后数值漂移。

4.5.1 一条总原则

读不到就用自己的上月值；从没读到过就用配置里的初始值。
绝不用 0（0 会被当成"真实值为零"，导致级联崩塌）。
情况下游行为
上游本月未产出沿用上月值，并标记 stale
从第一期就没产出（如 B3 阶段没有 utility）用 config/sim/&lt;系统&gt;.json 的 default 值
上游产出但值为 0当成真实 0（与"没有"区分）

⚠ "没有"和"是 0"必须区分。这是数值系统最基本的纪律： null（没有）≠ 0（有，但是零）。混在一起，"没建水厂"就会变成"水厂容量为 0"， 然后所有地块都不能长——而实际上 B3 阶段市政应该是无限供应。

4.5.2 各系统在"下游缺数据"时的默认值

读的 key谁读缺数据时的默认
utility.*_okzoningtrue（无限供应） ← B3 必须如此
employment.material_supplyzoningdefault（够用），不减速
population.demandzoning0（不生长）——这是真的 0
traffic.avg_commute_spopulation配置里的城市平均值
services.school_scorefinance1.0（无学区溢价）
finance.land_valuezoning按公式现算（它是派生量）

⚠ **utility.*_ok 的默认值是 true**：这是 B3 能通过验收的前提 （07-services §六 SV4 明确"B3 阶段市政视为无限供应"）。 如果默认成 false，B3 会"所有地块都不能长"，验收永远不过。

4.5.3 分阶段开关（比默认值更明确的做法）

批次谁没上线做法
B2–B3utility population employment services finance不读这些 key，用配置常量
B4utility services finance 部分同上
B5finance地价用可达性单因子
B6autilityutility.*_ok = true
B6b全部上线正常读

⚠ 优先用"分阶段开关"，而不是依赖默认值： 默认值是给"意外缺数据"兜底的，不是给"还没实现"用的。 两种情况的处理不该混。

五、怎么判断一个功能该归谁

按顺序问，第一个答"是"的就定了：

  1. 它是在"产生"一份数据，还是在"消费"别人已产生的数据？

→ 产生者拥有，消费者只读。

  1. 它的输出会不会被 ≥2 个系统读？

→ 会：它该独立成一个系统或至少一个独立文件。

  1. 它必须在 Tick 顺序的哪个位置？

→ 位置由"谁依赖它"决定。utility 就是靠这条从 services 里拆出来的。

  1. 它是不是只是别人的一个参数变化？

→ 是：不要新建系统，改参数（科技演进 F88 就是这么做的）。

⚠ 第 4 条最容易被忽略：很多"想要的新功能"其实只是某个已有系统的参数变了。 每加一个系统/文件之前，先问一遍这条。
