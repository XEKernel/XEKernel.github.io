渲染层选型：要不要把渲染换成 WebUI（Three.js）

## ⛔ 结论：已否决（R33，2026-11-22）
开发者拍板：「干脆还是继续 Godot 吧」。
本报告保留原样留档，理由与"重议触发条件（W-1/W-2/W-3）"见 decisions.md 的 R33。
留档价值：里面的工具链实测（MSVC 有 / SDK 缺 / MSYS2 遮蔽 link.exe）与 Three.js 实例化边界
（1–10 万、每帧写矩阵是瓶颈）以后仍有参考价值，不要删。
2026-11-22，开发者提出：「模拟等逻辑计算用 C#，渲染等用 WebUI，这样动画也好做，Three.js 也不错。」
本文是提案 + 可判定的实测计划。裁定已出：R33 否决，继续 Godot（见篇首横幅）。

〇、先说结论

这个方向值得认真试，而且现在是唯一低成本的窗口期 —— 但不要凭感觉换，先做一次 30–60 分钟能跑完的压测（§五）， 用四项硬指标决定。理由是：

  1. 你对 UI 的不满，是这套技术栈造成的，不是设计没想清楚。Godot 的 Control 节点在布局、动画、主题上都要手写坐标与 Tween；

Web 有 CSS 的 flex/grid + transition，同一件事的迭代成本差一个数量级。这一条换栈能结构性解决，调参解决不了。

  1. 现在换损失最小：scripts/view/ 还是 0 行实现（5 个占位文件），3D 渲染一行都还没写。

唯一会废弃的是 scripts/ui/ 那 1366 行 —— 而那正是你不满意的部分，废弃它反而省事。

  1. 模拟层已经天然可迁移：core/ 与 sim/ 按宪法 §四零 Godot 引用（138 条断言全在纯 .NET 里跑通）。

换句话说，这半年一直在为"引擎可换"做准备，只是没明说。

⛔ 不推荐"Godot 渲染 3D + 网页做 UI"的混合方案：需要在 Godot 里嵌 WebView（CEF 系集成不成熟、包体翻倍、输入焦点打架）。 要做就做整栈，别做半栈。

一、先把你这个想法拆成可检验的命题

#命题现状判断
1C# 只做模拟✅ 已经是事实（core/+sim/ 零引擎引用），不需要改架构，只需要把"宿主"从 Godot 换成一个普通进程
2WebUI 渲染更好做动画✅ 基本成立。CSS transition/WAAPI 比 Tween 省事；布局有 flex/grid，不用手写像素坐标
3Three.js 现在够用⚠ 分两半：静态建筑够用；每帧更新的车辆是硬瓶颈，见 §三
4换过去整体更省⚠ 不一定。UI 省 3–4 周，3D 基础件（剔除/LOD/地形流式）多花 2–4 周，净差可能只有 0–2 周

⚠ 命题 3 是我最担心的一条，也是唯一必须实测才能定的。

2.0.1 但现在构建不了 —— 两个原因都实测到了具体报错

#现象实测证据修法
1link.exe 被 MSYS2 抢走cargo build 报 link: missing operand after '\377\376' + Try 'link --help' —— 这是 GNU coreutils 的 link，不是 MSVC 的把 MSVC 的 bin\Hostx64\x64 前置到 PATH（或改用 Developer Command Prompt）
2修完 PATH 后又死在 SDKLNK1181: 无法打开输入文件"advapi32.lib"；再查 D:\Windows Kits\10\ 只剩 Catalogs/，没有 Include/、Lib/重装 Windows SDK 的 SDK 本体（注册表 KitsRoot10 = D:\Windows Kits\10\ 还在，但内容被清空了）

⚠ 顺带的影响：你那个 QzoneArchive 现在也构建不了（cargo build 会死在第 1 或第 2 步）。 不是代码坏了，是环境被清过。补回 SDK 即可，不用改任何代码。

⚠ 别把它当成"换不换 Web"的依据：这两条只决定打包体积（Tauri 3–10 MB vs Electron 80–200 MB）， 不决定"要不要把渲染改到 Web"。方向该不该转，看 §五 的四项指标。

三、Three.js 的真实边界（查证 + 换算到本项目）

查到的公开实测与经验值（2026）：

事实数据
InstancedMesh 动画实例数1 万–10 万 视几何复杂度；每帧在 JS 里改 4×4 矩阵是主要瓶颈
逐实例剔除的临界点>1 万 就要考虑上 WebGPU compute，CPU 端剔除撑不住
单体 InstancedMesh 的坑只有一个包围球，因此视锥剔除对它无效 → 必须按空间分块成多个 mesh
WebGPU vs WebGL（RTX 3060 级，5 万实例）42 fps → 118 fps；CPU 占用 65% → 15%

换算到城脉的负载：

负载数量在 Web 里的可行性
建筑（静态）5 万–15 万栋✅ 完全可行。静态实例不每帧上传矩阵；按 2km 瓦片分块后视锥剔除有效（这正是我们 11-scale 已定的分块方案）
地形100 万格（50 m 派生栅格）/ 2500 km²✅ 可行，但要自己写分块 mesh + LOD + 流式加载（Three.js 是库不是引擎，没有现成的）
车辆（每帧动）8 万基线 / 15 万上限⚠ 最危险的一项。8 万 × 16 float = 128 万 float/帧，纯 JS 写矩阵大概率超 16 ms 预算
人口数据1000 万✅ 无关渲染，只在 sim 侧

车辆的三条解法（需要 spike 验哪条够）：

  1. 只渲染视锥内：1080p 视野里通常只有 1–3 万辆车 → 回到可行区间（但要每帧做一遍剔除，成本自己扛）
  2. GPU 端推进：sim 只给"每辆车每 N 秒的路径控制点 + 时刻"，位置在 vertex shader 里按时间插值 → CPU 零更新
  3. 降低渲染数量：CS1 屏幕上真正能看清的车也就几千辆，其余用假车流/尾迹代替（这条与 11-scale 的 LOD 策略一致）

⚠ 顺带一个必须记住的教训（来自上面的查证）： 单体 InstancedMesh 只有一个包围球 → 视锥剔除失效，顶点着色器会把全世界都跑一遍。 这正是 11-scale §2.5 已经定的"按 archetype × 2km 区块分块" —— 这个设计在 Web 里同样是命门，换个栈也要照做。

维度评估

五、⭐ 建议：先做 spike（半天，不动主工程）

不动 scripts/，在 bench/web_spike/ 里做一次性压测，用真实数量级跑：

测什么怎么造
5 万栋建筑InstancedMesh，按 2km 瓦片拆成 100 个子 mesh，静态矩阵
2 万辆车每帧改矩阵（最坏情况）；再来一组用"顶点着色器插值"做对照
100 万格地形50m 网格，按瓦片分块，只加载视锥内 30 块
UI 层一组 DOM 面板（模拟左侧信息 + 底栏），验证 CSS 动画手感

判定指标（写死，避免"感觉还行"）

#指标门槛
11080p 平均帧率（WebGPU，视锥内 2 万车 + 5 万栋）≥ 30 fps，目标 60
2主线程单帧耗时（矩阵更新 + 场景更新，不含 GPU 等待）≤ 8 ms
3内存（任务管理器，Edge 单标签）≤ 1.5 GB
4进场景首帧≤ 5 s

停止条件：任一指标超 2 倍，且两天内优化不下来 ⇒ 放弃方案 A，回 Godot。 这条要写进 decisions.md（见 §七），因为"感觉还行"是最容易骗自己的判断。

七、要你拍的三件事（拍完我才动手）

#待定我的建议
1做不做 spike做。半天成本，能把"感觉"换成数字，且不污染主工程
2spike 过了转不转转（方案 A）。理由是 UI 是你的痛点且属结构性问题；网页试玩版对独立开发者价值大
3壳选哪个开发期 Edge 直开本地页面（0 成本、随时刷新）；发行期优先 Tauri（3–10 MB，你已经在 QzoneArchive 上跑通过，经验可复用）；Electron 作为退路（80–200 MB 但一致）。⚠ 用 Tauri 前先把本机环境修好：① MSVC bin 前置 PATH ② 补回 Windows SDK 的 Lib/Include。这两条只影响打包，不影响方向

⚠ 如果你更在意"别再折腾、尽快看到能玩的东西"，那保持 Godot也完全正当 —— 那就把 UI 的验收改成 "先用截图回归把布局磨到你能接受"，我会把每次改动都出前后对比图，用图说话而不是用文字说。
